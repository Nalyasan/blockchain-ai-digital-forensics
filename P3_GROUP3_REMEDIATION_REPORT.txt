## 2. Root Cause Analysis & Remediation Details

### 2.1 Gate G3-05 — Note SHA-256 Hashing & No File Probing

- **Deficiency Identified:** `forensics/evidence_identity.py:note_hash_bytes32()` conflated input validation with hash payload computation by doing `clean_note = note.strip()` and returning `0x + sha256_utf8(clean_note)`. Furthermore, `forensics/onchain.py:568` called `note_hash_bytes32(clean_note)`. This stripped leading and trailing whitespace contrary to Plan v2 §3.1 ("kể cả khoảng trắng đầu/cuối nếu note không rỗng").
- **Remediation Applied:**
  1. **Strict Input Validation vs. Hash Separation:**
     ```python
     if not isinstance(note, str):
         raise ValueError("Invalid note: must be a string")
     if not note.strip():
         raise ValueError("Invalid note: cannot be empty or whitespace-only")
     return "0x" + sha256_utf8(note)
     ```
  2. **Caller Alignment in `forensics/onchain.py`:** Line 565 preserves original `note` verbatim: `note_b32 = note_hash_bytes32(note)`.
  3. **In-Memory Guarantee:** Strictly zero filesystem calls (`os.path.exists`, `os.stat`, `open`, `Path.exists`, `Path.stat` patched to forbidden).
  4. **Comprehensive Test Suite in `tests/test_evidence_identity.py`:**
     - `test_note_hash_whitespace_verbatim_preservation`: Asserts `hash_base != hash_padded` and confirms both match exact `sha256(raw_bytes)`.
     - `test_note_hash_unicode_multibyte`: Accented Vietnamese, Japanese kanji/kana, unicode emojis (`🔒📦`), mathematical symbols.
     - `test_note_hash_long_content`: Lengths 512, 1024, 2048, and 8192 characters.
     - `test_note_hash_same_prefix_different_suffix`: Confirms distinct hashes for identical prefixes with varying suffixes or whitespace.
     - `test_note_hash_zero_leakage_in_exceptions`: Confirms raw note content is never echoed in exception messages or logs.

#### 2.7.2 BLOCKER 2 — G3-11: SQLite Migration Atomicity & Savepoint Transaction Boundary
- **Deficiency Identified:**
  - In Python's standard `sqlite3` library, invoking `conn.executescript(GROUP3_SCHEMA)` internally issues an implicit `COMMIT` before executing the script.
  - As a result, any transaction boundary opened by the caller was broken. If an error occurred mid-migration (such as a unique index collision on duplicate legacy rows), SQLite could not roll back the DDL statements, leaving partial tables or altered schemas behind.
- **Remediation Applied in `forensics/schemas.py`:**
  1. **Native SQLite `SAVEPOINT` Implementation:**
     ```python
     def migrate_group3(c: sqlite3.Connection) -> None:
         cur = c.cursor()
         cur.execute("SAVEPOINT migrate_group3")
         try:
             # Add columns conditionally
             ...
             # Execute DDL statements individually
             statements = [stmt.strip() for stmt in GROUP3_SCHEMA.strip().split(";") if stmt.strip()]
             for stmt in statements:
                 cur.execute(stmt)
             cur.execute("RELEASE SAVEPOINT migrate_group3")
         except Exception:
             cur.execute("ROLLBACK TO SAVEPOINT migrate_group3")
             cur.execute("RELEASE SAVEPOINT migrate_group3")
             raise
     ```
  2. **Zero Half-Written State:** If any statement fails, the entire migration rolls back cleanly to the savepoint, leaving exactly 0 Group 3 tables/columns added and 100% of legacy rows untouched.
  3. **AST Inspection & Atomicity Verification in `tests/test_onchain_blockers.py`:**
     - `test_migrate_group3_does_not_use_executescript`: Inspects source code to ensure `.executescript(` is never called.
     - `test_migrate_group3_atomic_rollback_on_unique_index_failure`: Verifies that unique index failure on duplicate rows leaves zero tables (`anchor_links`, `onchain_operations`, `onchain_operation_events`) created.
     - `test_migrate_group3_wal_mode_and_rerun_idempotency`: Verifies migration in WAL mode and confirms rerun idempotency.

#### 2.7.3 Final Targeted Security Audit Findings (Findings 1, 2, 3)

Following independent audit of commit `7e520c9`, three targeted findings were identified and resolved on commit `d50f880`:

1. **Finding 1 — G3-03: Incomplete ABI Event Data Accepted:**
   - *Vulnerability:* In `verify_receipt_and_event()`, `EvidenceRegistered` verified actor only if `len(data_hex) >= 66`, and `CustodyRecorded` verified artifact/note only if `len(data_hex) >= 130`. If `data="0x"`, checks were skipped, permitting false `verified=1`. In addition, `transactionHash` and `blockHash` only checked `.startswith("0x")` rather than verifying authentic 32-byte EVM hex.
   - *Remediation in `forensics/onchain_store.py`:*
     - Enforce `BYTES32_HEX_REGEX = re.compile(r"^0x[0-9a-fA-F]{64}$")` for mandatory 32-byte hex validation of `transactionHash` and `blockHash`.
     - Strictly validate ABI unindexed payload structure and length:
       - `EvidenceRegistered`: Unindexed data encodes `(address submitter, string storageUri)`, strictly requiring minimum 96 bytes (`>= 194` hex chars), offset == 64, URI length consistency, and submitter address matching `expected_actor`. Empty data `"0x"` or truncated payloads fail closed immediately.
       - `CustodyRecorded`: Unindexed data encodes `(bytes32 artifactSha256, bytes32 noteHash)`, strictly requiring exactly 64 bytes (`== 130` hex chars).
     - Unit tests in `tests/test_onchain_blockers.py::TestFinding1_EventDataAndHashValidation` prove that `verified=1` can never be written when event data is empty or invalid.

2. **Finding 2 — G3-10: Missing Canonical Block Accepted in Reconcile:**
   - *Vulnerability:* In `reconcile_operation()`, if `eth_getBlockByNumber` returned `None` or RPC client lacked block verification methods, canonicality could be bypassed, resulting in false `CONFIRMED` and `verified=1`.
   - *Remediation in `forensics/onchain_store.py`:*
     - Reconcile queries `eth_getBlockByNumber` and strictly asserts `block is not None` and is a mapping (`CANONICAL_BLOCK_NOT_FOUND`).
     - Require `block["hash"]` to match receipt `blockHash` (`NON_CANONICAL_BLOCK_OR_REORG`).
     - If RPC client lacks block verification methods, reject with `RPC_BLOCK_VERIFICATION_UNSUPPORTED`.
     - In all non-canonical, missing, or error cases, reconcile preserves `UNKNOWN` without broadcasting any transactions or mutating DB.
     - Unit tests in `tests/test_onchain_blockers.py::TestFinding2_ReconcileCanonicalBlock` verify all rejection paths.

3. **Finding 3 — G3-04: Unauthorized Automatic Migration:**
   - *Vulnerability:* In `forensics/onchain.py`, `record_custody_action` called `ops.pre_send_db_check(db_file, migrate=True)`.
   - *Remediation in `forensics/onchain.py`, `forensics/onchain_ops.py`, `forensics/onchain_store.py`, `forensics/cli.py`:*
     - Eliminated `migrate=True` from all write flows; changed `migrate_before_send=False` across `claim_send` and pre-send checks.
     - Placed `ops.pre_send_db_check(db_file, migrate=False)` in `anchor_evidence` and `record_custody_action` before any transaction preparation or network calls.
     - If DB is unmigrated, write flows fail fast with `GROUP3_SCHEMA_MISSING` with zero send and zero schema modification.
     - Added explicit operator CLI command: `python -m forensics.cli migrate-db --db <path>`. Production database is never automatically migrated.
     - Unit tests in `tests/test_onchain_blockers.py::TestFinding3_PreSendNoAutoMigration` verify fail-closed behavior and explicit CLI migration.

#### 2.7.4 Final Narrow Security Remediation (Findings A and B)

Following direct ZIP audit, two final narrow security findings were identified and resolved on commit `c62f5bb`:

1. **Finding A — G3-03 / G3-10: Event Storage URI Mismatch:**
   - *Vulnerability:* In `verify_receipt_and_event()`, checking only offset and minimum length of `storageUri` was insufficient: mutating a byte in the canonical URI (e.g. from `"e"` to `"X"`) was accepted, permitting false `verified=1` and false `CONFIRMED` reconciliation.
   - *Remediation in `forensics/onchain_store.py`:*
     - Decoded the complete ABI `storageUri` UTF-8 string including exact byte length.
     - Validated zero-padding bytes (`data_hex[194 + uri_len * 2 : expected_min_hex]`): any non-zero character raises `VERIFICATION_FAILED: non-zero padding in storageUri ABI data`.
     - Enforced exact length (`len(data_hex) == expected_min_hex`): any unexpected trailing data raises ABI violation.
     - Cross-validated `decoded_uri` against expected canonical storage URI constructed from `case_digest` and `manifest_sha256` (`evidence://sha256/<case_digest>/<manifest_hash>/manifest.json`).
     - Cross-checked URI path segments against indexed topics `topic[2]` (`case_digest`) and `topic[3]` (`manifestSha256`).
     - Profile enforcement: legacy mode rejects canonical URIs; canonical mode rejects legacy URIs; single-byte mismatches or digest mismatches fail closed with zero `verified=1` and zero `CONFIRMED`.
     - Reconcile mechanism strictly preserves `UNKNOWN` state on URI mismatch.
     - Targeted tests in `tests/test_onchain_blockers.py::TestFindingA_StorageUriStrictValidation` (6 tests).

2. **Finding B — G3-04: Implicit Migration via Exporter:**
   - *Vulnerability:* In `forensics/exporter.py`, `export_package` called `init_db(str(db_file))` which automatically ran `migrate_db() -> migrate_group3()`. Calling standard evidence export on an existing legacy SQLite DB implicitly upgraded its schema to Group 3, violating historical legacy database preservation.
   - *Remediation in `forensics/schemas.py`, `forensics/exporter.py`, `forensics/evidence.py`:*
     - `init_db(path, *, migrate_group3_schema: bool | None = None)` distinguishes between initializing a brand new DB (`is_new=True`) versus opening an existing database (`is_new=False`).
     - On existing databases, `migrate_group3` is NOT executed unless `migrate_group3_schema=True` is explicitly specified by the operator.
     - `export_package` and `export_evidence` pass `migrate_group3_schema=False`. Standard evidence export operations on pre-existing legacy databases create `evidence_exports` if needed, but preserve the historical schema completely untouched without creating `anchor_links`, `onchain_operations`, `onchain_operation_events`, or modifying `custody_events`.
     - Production database `data/forensics.db` is never modified.
     - Targeted tests in `tests/test_onchain_blockers.py::TestFindingB_ExporterPreservesLegacySchema` (2 tests).
#### 2.7.5 Final Narrow Security Remediation (Finding C — Canonical Custody NoteHash Verification)

Following independent audit of commit `c62f5bb`, one final narrow security finding was confirmed and resolved on commit `a79f240`:

1. **Finding C — G3-03 / G3-05 / G3-07 / G3-10: Canonical Custody NoteHash Plaintext Verification:**
   - *Vulnerability:* In `forensics/onchain_store.py::verify_receipt_and_event()`, `CustodyRecorded` verification accepted a zero-padded plaintext UTF-8 `noteHash` when `SHA256(stripped_plaintext)` matched the expected hash, even when `legacy_case_encoding=False` (canonical mode).
   - *Remediation in `forensics/onchain_store.py`:*
     - Enforced strict bytes32 equality (`log_nh == exp_nh`) between on-chain `noteHash` and expected SHA-256 hash in canonical mode (`legacy_case_encoding=False`).
     - Completely eliminated implicit zero-padding or plaintext fallback from canonical verification. Any mismatch immediately raises `VERIFICATION_FAILED: noteHash mismatch in CustodyRecorded log`.
     - Restricted legacy zero-padding plaintext verification strictly behind explicit, read-only `legacy_case_encoding=True`.
     - In `reconcile_operation()`, forwarded `legacy_case_encoding=bool(intent.get("legacy_case_encoding", False))` for `CustodyRecorded`. On noteHash mismatch, reconcile preserves `UNKNOWN` state with `reconciled=False`, zero `CONFIRMED`, and zero `verified=1`.
   - *Remediation in `forensics/onchain.py`:*
     - Updated `verify_custody_receipt(..., legacy_case_encoding: bool = False)`: in canonical mode, raw note fallback is strictly disabled and requires `data[32:] == _bytes(note, 32)`.
     - In `record_custody_action()` (new custody write path), explicitly set `raw_note=None` and `legacy_case_encoding=False`, strictly enforcing exact SHA-256 bytes32 equality in both `verify_custody_receipt` and `verify_receipt_and_event`.
   - *Targeted Tests in `tests/test_onchain_blockers.py::TestFindingC_CanonicalCustodyNoteHash` (8 tests):*
     - `test_canonical_verification_rejects_plaintext_padded_note_hash`: Asserts fail-closed on zero-padded plaintext in canonical mode.
     - `test_canonical_verification_accepts_correct_sha256_note_hash`: Confirms exact SHA-256 acceptance.
     - `test_canonical_verification_rejects_wrong_sha256_note_hash`: Confirms mismatch rejection.
     - `test_persist_verified_event_refuses_verified_1_for_plaintext_padded_note_in_canonical_mode`: Proves zero `verified=1` written.
     - `test_reconcile_custody_preserves_unknown_for_plaintext_padded_note_in_canonical_mode`: Proves operation in DB preserves `UNKNOWN`.
     - `test_explicit_legacy_profile_accepts_plaintext_padded_note_when_sha256_matches`: Verifies legacy opt-in compatibility.
     - `test_explicit_legacy_profile_rejects_plaintext_padded_note_when_sha256_mismatches`: Confirms legacy fail-closed on invalid data.
     - `test_verify_custody_receipt_enforces_exact_equality_in_canonical_mode`: Confirms helper enforces exact equality.

## 6. Operational Guidance & Known Limitations

1. **Verifying Historical Evidence Anchored Prior to Group 3:**
   - Operators verifying packages created before Phase 3 Group 3 must explicitly supply the `--legacy-case-encoding` CLI flag or pass `legacy_case_encoding=True` to `verify_onchain_evidence()`.
   - Successful legacy verification returns status `MATCH` with reason code `LEGACY_PUBLIC_CASE_ID` (exit code 0).
   - Canonical packages verified without the flag return status `MATCH` with reason code `OK` (exit code 0).
2. **Database Migration Policy:**
   - Pre-send checks `pre_send_db_check(migrate=False)` strictly require explicit schema migration (`python -m forensics.cli migrate-db --db <path>`) prior to write operations. Automatic mutation before send is disabled.
   - Standard evidence export on existing legacy databases preserves schema completely untouched without Group 3 tables.
   - Operations never perform `INSERT OR REPLACE` or backfill legacy rows.
3. **Recovery Procedures:**
   - Operations that encounter network timeouts or process terminations transition to `UNKNOWN`.
   - Operators should inspect `<db_path>.recovery.jsonl` and execute `python -m forensics.cli reconcile --operation-id <id>` in read-only mode to synchronize onchain confirmation without risking duplicate transaction submission.
